# 智能罗盘：三种日程区域与无向路径图

## 编辑与应用

以下均使用游戏动作名称，“使用”默认右键、“攻击”默认左键、“潜行”默认 Shift。

编辑现有配置时，可先选择菜单第一项“读取女仆配置”，使用自己的女仆，将她的全部区域、名称、路径图与调度复制到罗盘，覆盖原草稿。读取和编辑不改变女仆，需重新应用才生效；没有本模组配置时保留草稿。

1. 主手持智能罗盘，工具菜单（默认 Alt）选择“立方框选”，使用两角添加区域，默认是工作区。
2. 选择“标记选区”，使用框循环工作→休息→睡觉→工作。节点 UUID 和已有边保持不变。
3. 选择“路径节点规划”，使用已有区域或点选起点；走到必经位置，使用非已有节点的位置，记录玩家此刻脚部方块坐标并添加无向边。方块和空气交互均可。
4. 继续创建、连接或分支；使用另一已有节点可直接连接。相同边不会重复，同维度相同脚部坐标的点会复用。正在连线时攻击任意位置只取消起点；未连线时攻击点删除它和关联边，攻击区域只断开其边。无需结束操作，潜行+使用同普通使用。
5. 选择最后一项“应用到女仆”，使用自己的女仆，开启 Home。编辑工具不应用配置。潜行+使用女仆在应用工具中清除全部自定义配置。

潜行+清除键（默认 Shift+V）在立方框选工具清除三种立方区域、保留路径点和点间边；路径工具清除中间点、保留所有区域和区域间直接边。标记和应用工具不清除节点。每份图最多 256 点和 2048 边，区域总数由 maxAreasPerMaid 决定。

工作、休息和睡觉各自决定是否使用自定义区域：有该类型立方区时优先沿图，没有时使用 TLM 原罗盘的坐标和全部行为。两种罗盘数据独立，应用顺序不影响优先级；移除当前自定义类型时立即恢复原版区域，再回到自定义日程时从实际位置重新规划。

## 路线选择

工作、休息、睡觉区域和单格路径点都在同一无向图中。Dijkstra 按三维游戏坐标距离计算最短路线；跨维度段乘以 `dimensionDistanceMultipliers` 中对应无向配对的倍率，未配置为 1，同维度不换算，边可双向使用。

女仆在已知区域或路径点内时，从对应节点规划至目标。第一段距离以女仆实际当前位置计算，后续使用节点中心距离。若同时位于多个重叠节点内，比较有效路线并选择较短者。

女仆在所有节点之外时：

1. 遍历目标所在连通分量，即包含目标的最大连通子图。
2. 从这个分量与女仆同维度的全部节点中，按节点中心距离选最近的入口。工作区、休息区、睡觉区和中间路径点均参与，目标区域自身也可作为入口。
3. 先实际进入入口节点的框，再沿入口到目标的图上最短路线依次导航。更近但不连通的节点不会作为入口，经过其他类型的区域时仍保持当前日程和最终目的地，不开始该区域的任务。

入口按“最近节点中心”规则选择，即使另一个较远入口能缩短后续总路程，也先选最近节点。只有区域、没有中间路径点的图也能选择入口；最近入口是目标自身时，直接前往并进入目标框。目标分量没有与女仆同维度的节点，或当前所在节点不能连到目标时，回退到直接朝目标区域中心寻路；异维度目标仍遵守等待规则。

未自定义调度时工作区按添加顺序轮换；自定义表按条目目的地和各自延迟执行，下一条目标同样通过图规划。休息和睡觉在日程开始时，分别对各候选区执行上述规划，计算“女仆→入口/首节点→后续节点→目标”的距离总和，选择有合法图路线且总和最小的候选。所有候选都无图路线时，以直接距离选择。女仆已在某个对应候选区内时，到该区的路程为零。

这里的距离是坐标之间的三维欧氏距离，不是先运行各段 A* 后得到的真实绕障路程。玩家需要把节点放在可站立位置，并保证相邻节点之间可通行。

## 实际导航与日程

无论 WORK、IDLE 还是 REST，当前段始终朝节点中心寻路，脚部进入该节点的框即可推进。

必须完成全部必经节点并进入最终区域，才恢复对应日程的任务行为。提前进入最终区域不能跳过剩余路线。图路线期间 TLM 周期返回目标始终是当前节点，禁用日程返回传送兜底，避免跳过节点；无图直接导航保留原兜底。

日程变化后重新选择目的地和路线。工作区域游标和游戏刻进度独立于休息、睡觉目的地；睡醒后返回原工作区域继续额度。没有该类型自定义区域时沿用 TLM 原日程区域。转场超时默认 0，关闭超时跳过；设置正数时单段按允许移动的游戏刻计时，超时工作跳至下一工作区，休息和睡觉尝试其他候选。

## 第二版数据结构（已实现）

发布版本 2.0.0 使用下面的第二版存储格式，网络协议独立升为 7。保留现有同步方式；跨维度路线等待外部机制转移女仆，异步传输与增量同步尚未实现。

### 身份与节点

每个区域和中间路径点具有创建时生成的 UUID。改名、改区域类型、调整坐标、重排显示顺序、保存重载、读取女仆配置和重新应用时都保留此 UUID。删除后重新框选是创建新节点，生成新 UUID。不同维度的相同坐标也不是同一节点。

区域和路径点统一保存在 `nodes` 列表中。每个元素包含自己的属性，不再使用坐标、类型、名称三个平行列表，也不再用正负下标区分节点。

| 节点字段 | 类型 | 约定 |
| --- | --- | --- |
| `id` | UUID | 必填；同一计划内唯一，生命周期内不变 |
| `dimension` | 资源位置字符串 | 必填，例如 `minecraft:overworld`；属于该节点 |
| `type` | 字符串枚举 | `work`、`idle`、`sleep`、`waypoint` |
| `name` | 字符串 | 默认空字符串，沿用当前名称长度和清洗规则 |
| `min` | 三个整数 | 包含边界的最小方块坐标 |
| `max` | 三个整数 | 包含边界的最大方块坐标 |

`waypoint` 的 `min` 必须等于 `max`，因此它直接是一格大小的立方区域。工作、休息和睡觉区域也可以只有一格，由 `type` 区分用途。仍以脚部方块坐标进行严格包含判定，不加入地板站立层补偿。

`nodes` 的顺序只决定显示顺序，以及未设置自定义调度时的默认工作区轮换顺序。节点寻址、边和目的地引用均不依赖该顺序。界面可以显示编号，但编号仅是显示信息，名称也不作为身份。

UUID 在实际 NBT 中保存为四整数数组，不保存为 UUID 字符串。下文的简单 UUID 仅用于让示例中的引用容易对应；实际创建使用随机 UUID。

### 计划格式

计划的 `data_version` 升为 `2`。继续使用原物品组件名 `touhou_little_maid_custom_workspace:workspace_plan`。

| 计划字段 | 约定 |
| --- | --- |
| `data_version` | 当前计划格式版本，第二版为 `2` |
| `plan_id` | 计划创建时生成的 UUID，用于标识配置来源；编辑和快照复制保留 |
| `nodes` | 完整节点列表 |
| `edges` | 无向边列表，端点为节点 UUID |
| `work_schedule` | 调度条目和循环设置，空条目列表表示使用默认轮换 |

计划顶层不再保存统一 `dimension`。罗盘可以保存多个维度的节点，各节点的归属独立。以下为可以表达的 NBT 结构示例，默认字段可省略：

```snbt
{
  data_version: 2,
  plan_id: [I; 1,16384,-2147483648,1],
  nodes: [
    {
      id: [I; 1,16384,-2147483648,101],
      dimension: "minecraft:overworld",
      type: "work",
      name: "菜田",
      min: [I; 0,64,0],
      max: [I; 4,67,4]
    },
    {
      id: [I; 1,16384,-2147483648,201],
      dimension: "minecraft:overworld",
      type: "waypoint",
      min: [I; 8,64,5],
      max: [I; 8,64,5]
    },
    {
      id: [I; 1,16384,-2147483648,102],
      dimension: "minecraft:overworld",
      type: "work",
      name: "果园",
      min: [I; 20,64,0],
      max: [I; 24,67,4]
    },
    {
      id: [I; 1,16384,-2147483648,103],
      dimension: "minecraft:the_nether",
      type: "idle",
      name: "下界休息室",
      min: [I; 0,64,0],
      max: [I; 4,67,4]
    }
  ],
  edges: [
    {a: [I; 1,16384,-2147483648,101], b: [I; 1,16384,-2147483648,201]},
    {a: [I; 1,16384,-2147483648,102], b: [I; 1,16384,-2147483648,201]}
  ],
  work_schedule: {
    cyclic: 0b,
    entries: [
      {
        id: [I; 1,16384,-2147483648,401],
        destination: [I; 1,16384,-2147483648,101],
        condition: {type: "delay", ticks: 2400}
      },
      {
        id: [I; 1,16384,-2147483648,402],
        destination: [I; 1,16384,-2147483648,102],
        condition: {type: "delay", ticks: 1200}
      }
    ]
  }
}
```

`plan_id` 表示配置来源，不代表全球唯一的一份可变配置。同一个罗盘应用给多个女仆时，她们可以保留同样的计划 ID 和节点 ID，但各自保存独立快照；修改某份快照不会修改其他副本。节点引用只在所属计划内解析，不通过全局节点表取得数据。同一计划 ID 也不保证内容相同，编辑提交仍校验预期快照，不用计划 ID 替代内容校验。

新建节点生成新 UUID；复制整份罗盘或读取女仆保留已有身份。将来若加入“复制单个区域”或“导入并合并”功能，新增的复制节点需要新 UUID，或明确处理身份冲突，不能仅按坐标、名称或列表位置合并。

### 图边与调度引用

边保存两个节点 UUID，不保存坐标、维度或显示编号。维度从端点节点取得。两端必须存在且不同，允许属于不同维度。无向边按固定的 UUID 比较规则规范化端点顺序并去重；节点重排、改名、工作/休息/睡觉类型切换均不改变已有边。节点的位置和维度被调整后，重新校验边。

允许跨维度连线与路线规划。边的计费距离为节点坐标间三维欧氏距离乘以维度配对倍率，两个方向一致；未配置的配对倍率为 1。女仆到达下一节点前逐刻比较维度，维度不同则等待外部机制转移，路径导航不主动发起跨维度传送。

`MaidDimensionChangeMixin` 在 TLM 的 `changeDimension` 方法入口调用父类实现并取消 TLM 方法体，恢复原版实体转移流程。跨维度时按原版行为创建实体副本并复制 NBT，本模组的配置和工作进度随女仆数据保留；NeoForge 传送事件和 `DimensionTransition` 回调同样保留。传送门或外部模组负责触发转移，成功转移到不同维度后将旧导航标记为待重规划，下一次导航按新维度和实际落点选择图入口。被取消的转移和同维度转移不触发这个维度变更检查点。

以上实体转移兼容由 `maidDimensionCompatibility` 总开关控制，默认开启。同一开关将女仆继承的传送门冷却从 300 游戏刻改为与原版玩家相同的 10 游戏刻；保留原版冷却逐刻递减、冷却期间接触传送门会刷新冷却的规则。关闭后 `changeDimension` 注入不取消 TLM 方法体，恢复 TLM 的转移处理及父类原有冷却，也不执行该转移兼容入口的重规划。区域、路径图和运行数据不会因开关切换而删除，Home 状态切换的重规划独立生效。

调度条目拥有独立 UUID，`destination` 引用 `work` 节点。相同工作区可以出现在多个条目中，条目的延迟与执行身份分别保存。重排条目不改变条目 UUID；复制条目生成新条目 UUID，仍可引用同一目的地。条件仍仅为一个 `{type:"delay", ticks:...}` 对象，本次不添加新条件或条件组合。

修改区域类型为非工作区时，沿用现有编辑行为，移除目的地为该节点的工作调度条目；图边保留。删除区域时移除该节点、关联边和相关调度条目；删除路径点时移除该点和关联边。所有仍存在的节点及条目 ID 保持不变，绝不重新编号。

### 女仆配置与运行状态

继续通过 TLM 的 `MaidTaskDataMaps` 保存，键名保持 `touhou_little_maid_custom_workspace:workspaces`。女仆外层 `data_version` 同样升为 `2`，与内部计划版本独立：

```text
MaidTaskDataMaps
└─ touhou_little_maid_custom_workspace:workspaces
   ├─ data_version: 2
   ├─ plan: 上述完整第二版计划
   └─ runtime
      ├─ schedule_type: work / idle / sleep
      ├─ phase: travel / active / suspended / waiting_dimension
      ├─ destination: 最终目的地区域 UUID，可省略
      ├─ remaining_route: 尚未抵达的节点 UUID 列表
      └─ work
         ├─ destination: 保留的工作区 UUID，可省略
         ├─ entry: 当前自定义调度条目 UUID，可省略
         ├─ elapsed_ticks: 当前工作阶段累计游戏刻，Long
         └─ finished: 非循环工作调度是否结束
```

`runtime.destination` 是当前工作、休息或睡觉的最终目的地，必须是对应类型的区域。途中导航目标取 `remaining_route` 的第一个元素；列表最后一个元素必须是最终目的地。没有图路线、直接导航时，列表为空。抵达节点从列表头移除，抵达最终区域后变为 `active`。休息或睡觉时，`work` 保留工作区、条目和计时，不能用休息区覆盖工作目的地。

`suspended` 表示该自定义日程状态暂不参与导航或等待重规划，例如当前日程使用原版区域、Home 状态切换或实际维度变化；可以保留之前的路线和工作进度，但不执行该路线，恢复自定义导航后从实际位置重新规划。没有目的地用字段缺省表达，不使用下标 `-1` 或全零 UUID 作为空值。默认轮换没有自定义条目时不保存 `work.entry`。

读取女仆只复制 `plan`，编辑不修改女仆。重新应用仍按现有行为初始化运行状态，从实际位置重新规划，工作计时与调度执行进度重置；本次不改变这个应用语义。迁移已有存档不属于重新应用，必须保留旧运行进度。

正常计时仍只更新运行对象，沿用现有同步入口。完整计划仍按现有规则同步，本次不将其拆成不同网络协议或异步任务。运行时可以建立 UUID→节点查找表；这类派生索引不保存进 NBT，也不作为稳定身份。

### 维度与编辑边界

高亮、命中检测、选区包含和任务候选目标搜索均先检查节点维度，图寻路允许使用跨维度边。图外入口从女仆当前维度的所有节点中选择；最终区域候选可以属于其他维度。另一个维度的相同 XYZ 不能被视为命中或到达。整份计划没有对应日程类型的立方区时，沿用 TLM 原版区域逻辑；只有异维度区域时仍以该区域为目的地，在下一异维度节点处等待。

同一罗盘可继续在其他维度添加节点，已有节点保留原维度。临时框选第一角包含维度和坐标，不写入存档；切换维度取消未完成的立方框选。路径起点 UUID 保存在持久组件 `route_anchor` 中，换物品、换模式、换维度、保存重载、读取配置和批量清除均不隐式取消。只由攻击键取消；若删除或替换计划使该起点失效，提示玩家先攻击取消，再选择新起点。第一版起点原本不持久，因此无旧存档字段需要迁移。

应用时保持所有节点的维度，不把整份计划改成女仆当前维度，不主动加载节点区块。下一导航节点（或无图路线时的最终区域）与女仆维度不同时，进入 `waiting_dimension`，停止导航和任务动作，保留完整剩余路线、目标、调度身份和工作刻数，不增加转场超时计数。实际跨维度后重新规划，不再等待已留在原维度的未完成节点；新的同维度节点仍须精确进入才推进，不得因异维度坐标相同而推进。没有该日程类型立方区时才回退 TLM 原逻辑。

女仆 NBT 加载期间不重新选择日程路线，避免原版跨维度实体复制期间的临时坐标参与选入口。同维度区块重载后，已有非空剩余路线继续保留；若此前因所在维度没有入口而留下空的直接回退路线，恢复导航时重新寻找连通图入口。Home 状态切换和成功跨维度共用一个导航失效入口，立即持久化待重规划标记；重新开启 Home 或跨维度完成后，按当前日程和实际位置重新规划，即使关闭后用魂符移动且期间没有实体 tick 也能恢复。休息、睡觉候选区重新比较路线距离，配置、工作目的地、调度条目和累计工作刻数不重置。

### 公共访问检查点与第一版迁移

`WorkspaceAccess` 是业务代码读取和修改罗盘、女仆配置的公共入口。物品组件和 TLM TaskData 的存档、网络 Codec 在进入这一访问层之前统一经过 `WorkspaceDataVersions`，先迁移原始格式，再解码第二版模型。`WorkspaceLegacyMigration` 独立处理旧下标与平行数组；编辑器、界面、导航和 Mixin 均只操作第二版 UUID 对象。无法解码的数据用停用对象携带原始 Dynamic，保存时原样输出；访问层拒绝使用和修改它，避免 TLM 的空值加载问题。

无版本号数据先按已有 `0→1` 规则补齐默认值，再进行 `1→2`。迁移先建立全部身份映射，再一次性转换计划和女仆引用，不能分别解码时各自生成不对应的随机 UUID。

1. 规范化第一版计划的逻辑内容：展开默认值，保留区域、点和调度的顺序，规范化无向边端点及边顺序。使用固定模组命名空间前缀和规范化内容生成确定性的 `plan_id`。
2. 在此计划 ID 下，按旧节点类别与旧下标生成确定性节点 UUID，例如 `area:0`、`area:1`、`point:0`；这些下标只用于一次迁移，第二版之后不再作为身份。
3. 将旧 `areas[i]`、`area_types[i]`、`area_names[i]` 合成一个节点。旧顶层 `dimension` 复制到每个节点。旧 `points[j]` 变为 `waypoint` 节点，`min=max=points[j]`。
4. 按映射将所有边端点转换为 UUID：旧非负编号查区域映射，旧负编号按 `j=-编号-1` 查路径点映射。
5. 按旧条目位置生成调度条目 UUID，旧 `area` 转为目的地 UUID，延迟和循环设置不变。重复目的地的条目保持各自身份。
6. 使用同一份计划转换所得的映射转换女仆：`active_index→runtime.destination`、`work_index→runtime.work.destination`、`schedule_index→runtime.work.entry`，并转换全部剩余路线。保留工作刻数、日程类型和完成状态。没有自定义调度时不制造条目引用。
7. 依据旧日程、目的地类型及旅行状态设置 `phase`。原版日程回退状态迁移为 `suspended`，保留有效工作进度，并在以后回到自定义日程时从实际位置规划。
8. 完整转换和校验成功后，才输出第二版版本号。再次读写第二版数据只保留其 ID，不重复生成身份。

确定性迁移使逻辑相同的旧罗盘和旧女仆快照得到相同身份，也使同一份尚未保存的旧 NBT 重复解码不会变换 UUID。第一版从未保存真正的稳定身份，因此已经分别编辑、逻辑内容不同的旧副本无法可靠恢复共同历史身份；迁移不会猜测它们是否曾来自同一罗盘。

### 完整性与兼容性要求

第二版必填字段缺失、UUID 重复、边引用缺失节点、调度目的地不是工作节点，以及非法范围等情况必须明确报告，不能用取模、重新编号、按坐标碰撞替代等方式指向另一个合法节点。正常编辑导致的关联删除由编辑操作完成，解码不静默删除图边或调度条目。

运行状态中的无效剩余路线可以显式作废并标记重新规划，不能被当成已经抵达最终区域；有效工作目的地、条目和计时应保留。完全失效的目的地暂停自定义状态，不能自动绑定同一列表位置的新节点。配置错误和未知未来版本必须保留原始数据并停用相应自定义配置，不能让 TLM 接入层收到未处理的空值，也不能用空计划覆盖原数据。

仍保留现有数量、名称和范围限制：区域类型节点受区域数量配置限制，`waypoint` 最多 256 个，边最多 2048 条，调度最多 128 条，名称最多 64 个字符。`data_version` 只表示存储结构；模组发布版本、网络协议版本和当前工具模式编号独立。实现时旧组件名与女仆键名保持不变，工具模式编号不变，网络引用从下标改 UUID 时单独升级网络协议。

回归验证覆盖：删除与重排不改变存活身份；重复调度目的地不混淆条目；同坐标不同维度不误命中；读取、复制、编辑、重新应用的快照相互独立；旧罗盘和旧女仆计划迁移一致；工作计时及未完成路线迁移保留；迁移幂等；异常及未知版本不会覆盖原数据。本设计不包含异步传输或性能优化实现。
